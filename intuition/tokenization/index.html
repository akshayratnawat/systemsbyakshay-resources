Tokenization: How LLMs Actually Read Text

The compression step before the model does any thinking - and the source of half the "AI bugs" that aren't model bugs at all

1. The Core Mechanism

An LLM never sees your words. It sees integers. Before a single weight in the model does any work, your text is run through a separate, much dumber system called a tokenizer, which chops it into chunks and maps each chunk to an integer ID from a fixed vocabulary. That vocabulary - usually 128K to 200K entries - was learned once, offline, by a completely different process than the one that trains the model.

The algorithm behind almost every production tokenizer is byte-pair encoding (BPE). It starts from raw bytes and repeatedly merges whichever adjacent pair of symbols is most frequent in the training corpus, growing a vocabulary of chunks until it hits the target size. Text that looked like this training corpus a lot - common English words, common code patterns - collapses into very few tokens. Text that looked nothing like it - rare words, most non-English languages, unusual formatting - shatters into many.

Byte-Pair Encoding, One Line
bytes → merge(most_frequent_pair) × N → vocab (128K-200K) → token_ids

That single compression step, run before the model exists in the pipeline at all, is the hidden variable behind almost every property people attribute to "the model": cost, latency, how much context you actually get, why arithmetic is unreliable, and why the same product costs more to run in some languages than others.

The individual letters "s-t-r-a-w-b-e-r-r-y" are never in the model's input. Only the two chunk IDs are. That is the whole reason it fumbles letter-counting.

2. Why "Count the R's in Strawberry" Isn't a Model Bug

"The model reads my words" is the assumption almost everyone brings to an LLM, and it's wrong in a way that explains a specific, famous failure. Ask a model to count the letters in "strawberry" and it often gets it wrong - not because it can't count, but because it's counting over the wrong representation. "Strawberry" doesn't arrive as nine letters. It arrives as two or three chunks, something like str + awberry. The letters inside those chunks were never separate symbols the model could attend to individually.

The reframe: spelling, letter-counting, and string-reversal aren't "reasoning" failures. They're representation failures - you're asking a model to operate on information that was thrown away before the model ever ran. No amount of prompting fixes a missing input.

3. Five Things About Tokenizers Most Posts Skip

These don't show up in the average "what is tokenization" explainer, but they're the ones that actually bite you in production.

FactWhat It MeansSource
The 15x language taxThe same sentence can cost up to 15x more tokens in a poorly-tokenized language than in English. That's 15x the cost, 15x the latency, and 1/15th of the effective context window for identical meaning. A "128K context" model can be an ~8K-context model for some markets.Petrov et al., NeurIPS 2023
Digits fragment inconsistentlyOlder tokenizers could split "380" into one token and "381" into two ("3" + "81"). Multi-digit numbers land unpredictably, which is a direct cause of arithmetic errors. Modern tokenizers (Llama 3, o200k) force digits into fixed 1-3 digit groups specifically to fix this.CS336 L1 / tokenizer configs
Trailing spaces are real tokens"Hello" and "Hello " are different token sequences. A prompt that ends in a stray space pushes the model off the distribution it was trained on - completion quality drops and few-shot formats break, silently.tiktoken (measured below)
The 3x throughput cliffVocab size isn't just a modeling choice - it's a GPU efficiency choice. Netflix's post-training team padded vocab size to a GPU-friendly multiple of 64/128 to avoid a ~3x embedding-layer training slowdown from bad tensor-core tiling.Netflix TechBlog
Glitch tokensTokens like " SolidGoldMagikarp" existed in GPT-2/3's vocab - artifacts from Reddit usernames in the tokenizer's training data that never showed up meaningfully in the model's training data. Their embeddings were essentially untrained, and prompting them produced bizarre, unstable output.Rumbelow & Watkins, 2023
The pattern underneath all five: the tokenizer is trained separately from the model, on its own objective (compress this corpus well) with no awareness of what the model will later need to do with the result. Every one of these facts is a symptom of that split.

5. Where This Breaks In Production

The multilingual bill shock

A product launches in a new market - say, Tamil or Hindi. Same user behavior, same feature usage. The token bill multiplies and the latency SLA blows up, because output tokens stream one at a time and there are simply 5-15x more of them for the same meaning. Nobody changed the model. The tokenizer was never fair across languages to begin with.

The whitespace regression

A prompt template gets refactored. Somewhere in the diff, a trailing newline or space is added or removed. Eval scores drop a few points. On-call spends a day chasing a "model regression" that doesn't exist - it's one invisible character that shifted every downstream token in the sequence.

The pretty-print tax

Debug-friendly, indented JSON with descriptive keys gets copy-pasted straight into a system prompt because it's what the logs already look like. It reads great for humans. It costs roughly 40% more tokens than it needs to, on every call, forever, for no benefit the model can use.

7. Why This Is the First Lecture, Not a Footnote

Stanford's CS336 opens its LLM systems course with tokenization before it touches attention, training, or scaling laws - and that ordering is the point. Everything downstream of the tokenizer inherits its decisions. Cost, latency, effective context length, arithmetic reliability, and multilingual fairness aren't separate model properties you tune later. They're consequences of a compression step that already happened by the time the model sees anything.

Treat the tokenizer like the versioned, measurable production dependency it is - not an invisible preprocessing step you never have to think about. The teams that measure it stop being surprised by their bills, their evals, and their arithmetic bugs.

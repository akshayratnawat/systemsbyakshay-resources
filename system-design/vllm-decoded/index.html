Module 1 - Foundations

1. Engine Anatomy

You call LLM(model=...) once. Before it ever sees a prompt, vLLM resolves its config, builds the scheduler, and - critically - runs a worker init sequence that decides two things you'll live with for the life of the deployment: how much GPU memory you actually get, and how fast your first request will be.

The decision that actually matters here

Decision: gpu_memory_utilization vLLM checks your VRAM against this value - default 0.8 - and treats it as a hard ceiling it will never cross unless you raise it. Set it too high and you OOM against anything else sharing the GPU. Set it too low and you're leaving concurrent-request capacity on the table. This single number is the difference between "fits" and "doesn't" for a given model + hardware pair.
llm = LLM( model="meta-llama/Llama-3.1-8B", gpu_memory_utilization=0.9, # raise from the 0.8 default if nothing else shares the GPU )

The cold-start tradeoff

During init, vLLM loads weights, then runs a real profiling forward pass to compute how many KV cache blocks fit in whatever VRAM is left. Unless you pass enforce_eager=True, it then captures a CUDA graph per warmup batch size - a recorded DAG of kernels it can replay instead of re-launching kernels on every step.

Weights are fixed once you pick a model. The KV cache budget - the part you actually control - is whatever's left under the ceiling.
Decision: enforce_eager True = faster, lighter startup, slower steady-state generation. Reach for it while iterating or debugging. False (default) = slower startup, faster steady-state. This is the right choice for anything stable in production - you pay the cost once at boot, not on every request.
# dev / debugging - fast to boot, skips graph capture llm = LLM(model="...", enforce_eager=True) # prod - slower to boot, faster steady-state generation llm = LLM(model="...", enforce_eager=False)

The formula behind every OOM you'll see

bytes_per_block = 2 * block_size * num_kv_heads * head_size * dtype_bytes # defaults: block_size=16, dtype_bytes=2 for bf16 # the 2 is for key and value, stored separately

Plug in your model's num_kv_heads and head_size and you can predict your memory ceiling before you hit it, not after. This is also a legitimate system-design interview question - "how much memory does a KV cache block use" is a straightforward arithmetic answer once you know this formula.

Module 2 - The Core Mechanism

2. Scheduler, Continuous Batching & Paged Attention

This is the single mental model everything else in this guide either exploits or works around. Get this one and the rest of vLLM stops looking like a pile of features and starts looking like consequences of one design choice.

Two workloads, two bottlenecks

WorkloadWhat it doesBottleneck
PrefillForward pass over the entire prompt, once, to produce the first tokenCompute-bound
DecodeForward pass over just the newest token, repeatedlyMemory-bandwidth-bound

Older serving engines could only run one type of workload per step. vLLM's scheduler can mix both in a single step - decode requests from the running queue get priority (they're already paying rent on KV cache memory), then prefill requests fill whatever budget is left from the waiting queue.

Why This Is the Interview Answer "How does vLLM achieve high throughput?" The answer is continuous batching: instead of waiting for an entire batch to finish before starting the next one (static batching, where a GPU can sit idle waiting for the slowest sequence), vLLM flattens all active sequences into one "super sequence" every step, with position indices and attention masks keeping them from bleeding into each other. No padding waste, no idle GPU time waiting on stragglers.

Your real concurrency limit is memory, not request count

Every request needs KV cache blocks to hold its growing context. The scheduler's allocate_slots call computes ceil(num_new_tokens / block_size) blocks needed and pulls them from a free_block_queue. When that queue runs dry, new requests wait - regardless of how much compute you have spare.

This is why vLLM doesn't need to wait for a "batch" to fill - every step is its own mixed batch, assembled fresh.
System Design Takeaway When you're capacity planning, don't think in "requests per second" in isolation. Think: (available KV cache blocks) ÷ (average blocks per request) = your real concurrency ceiling. Reducing average context length or raising gpu_memory_utilization both directly raise this number - reducing model size does not, since weights are a fixed cost paid once.
Module 3 - The Levers

3. Prefix Caching

If two requests share the same opening tokens - a system prompt, a few-shot block, a long document prefix - vLLM can skip recomputing the KV cache for that shared portion entirely and just reuse it.

How it actually works

Tokens are split into 16-token chunks (matching the default block size) and hashed. The hash for each chunk depends on the previous chunk's hash plus its own tokens - so a shared prefix produces identical hashes across requests, and find_longest_cache_hit can look up already-computed blocks instead of recomputing them.

The Decision This Actually Drives Put static content (system prompts, tool definitions, few-shot examples) at the START of your prompt, and put the variable, per-request content at the END. Every byte you put before the variable part is a byte that gets reused across every request sharing that prefix - and every byte after it breaks the cache hit for anyone whose prefix differs even by one token before that point.
# enabled by default - explicit for clarity llm = LLM( model="...", enable_prefix_caching=True, ) # prompt structure that actually benefits: # [ fixed system prompt ][ fixed tool definitions ][ VARIABLE user query ] # reused reused recomputed only
Where This Pays Off Most Long, static system prompts (agent instructions, RAG context templates) repeated across thousands of requests. This is close to free capacity - you're not adding hardware, you're just not re-doing work you already did.

4. Chunked Prefill

A single very long prompt can monopolize an entire scheduling step, blocking every other request - including latency-sensitive decode requests - until it's done.

The Tradeoff Set long_prefill_token_threshold to cap how many tokens of a long prompt get processed per step - the rest spreads across subsequent steps automatically. Lower values improve fairness and tail latency for other requests sharing the engine. Higher values (or leaving it unset) processes long prompts faster in isolation, at the cost of blocking everyone else while it runs.
Chunking trades a bit of raw throughput on the long prompt for much better tail latency on everything else.

5. Speculative Decoding

Every token normally costs a full forward pass through the large model. Speculative decoding proposes several tokens cheaply, then verifies them all in a single large-model pass - accepting the ones that match what the large model would have generated anyway.

The accept/reject math

For each of the k proposed tokens, left to right: if the large model's probability for that token is ≥ the draft's probability, accept it. Otherwise, accept it with probability p_large / p_draft. Stop at the first rejection. If all k are accepted, you also get one extra token "free" from the large model's own distribution.

The Real Decision vLLM's V1 engine doesn't support a separate draft LLM - it uses n-gram matching (fast, no extra model, works best on repetitive/structured output), EAGLE (a lightweight MLP replacing the transformer stack), or Medusa (auxiliary prediction heads). The tradeoff is acceptance rate vs. draft cost: n-gram is nearly free but only helps when output has repeated patterns; EAGLE/Medusa need training but generalize better. Worth it when decode latency, not throughput, is your bottleneck.
speculative_config = { "method": "ngram", "prompt_lookup_max": 5, "prompt_lookup_min": 3, "num_speculative_tokens": 3, } llm = LLM(model="...", speculative_config=speculative_config)

6. Guided Decoding

If you need output in a specific format - JSON matching a schema, one of a fixed set of choices - guided decoding constrains which tokens the model is even allowed to sample, using a grammar-based finite state machine.

When To Actually Use This Reach for guided decoding when malformed output is a hard failure (breaking a downstream parser, an API contract), not just an inconvenience. It has a real cost - grammar compilation and per-step logit masking - so for loose formatting preferences, prompting alone is usually cheaper and good enough.
from vllm.sampling_params import GuidedDecodingParams guided = GuidedDecodingParams(choice=["Positive", "Negative"]) sampling_params = SamplingParams(guided_decoding=guided)
Module 4 - Scaling Out

7. Scaling to Multi-GPU

When a model's weights don't fit on one GPU, you have two ways to split it - and the choice is a real architecture decision, not a default to accept.

ApproachSplitsBest when
Tensor Parallelism (TP)Individual layers, across GPUsGPUs share fast intranode bandwidth (e.g. NVLink) - prefer this first
Pipeline Parallelism (PP)Groups of layers, across nodesYou've exhausted TP within a node and must cross nodes - internode bandwidth is much lower, but PP communicates less data than TP would across that same link
Decision Rule Prefer TP over PP whenever your GPUs are in the same node. Only reach for PP when you've hit the ceiling of a single node's GPU count and must span multiple nodes - the bandwidth gap between intranode and internode links is the entire reason this ordering exists.
# 8 GPUs in one node, TP only llm = LLM(model="...", tensor_parallel_size=8) # spanning nodes: TP within each node, PP across nodes llm = LLM(model="...", tensor_parallel_size=8, pipeline_parallel_size=2)

8. Distributed Serving

Beyond a single engine, vLLM supports data-parallel deployment - multiple full engine replicas, load-balanced behind one API surface.

# Node 1 - headless (no API), 2 engines, TP=4 each vllm serve <model> \ --tensor-parallel-size 4 \ --data-parallel-size 4 \ --data-parallel-size-local 2 \ --data-parallel-start-rank 0 \ --data-parallel-address <master-ip> \ --data-parallel-rpc-port 13345 \ --headless # Node 2 - runs the API server, 2 more engines vllm serve <model> \ --tensor-parallel-size 4 \ --data-parallel-size 4 \ --data-parallel-size-local 2 \ --data-parallel-start-rank 2 \ --data-parallel-address <master-ip> \ --data-parallel-rpc-port 13345
How Requests Get Routed A coordinator scores each engine by len(waiting) * 4 + len(running) and routes new requests to the lowest score - waiting requests are weighted heavier since they represent latency the request hasn't started paying yet.
The Decision This is horizontal scaling for throughput, not a way around the TP/PP decision above - each replica still needs its own TP/PP configuration to fit the model. Add data-parallel replicas when you need more aggregate throughput than one engine (however parallelized internally) can serve.

9. Disaggregated Prefill/Decode

Prefill (compute-bound) and decode (memory-bandwidth-bound) have fundamentally different performance profiles. At large enough scale, running them on separate, independently-scaled pools of hardware gives you tighter control over both.

When This Earns Its Complexity This is real operational overhead - a KV transfer connector, two autoscaling policies, more moving parts to monitor. It earns that cost when prefill-heavy and decode-heavy traffic patterns interfere with each other badly enough on a shared pool that tighter latency control (TTFT and ITL independently) is worth the added system complexity. Below that scale, a shared pool with continuous batching (Module 2) is simpler and usually sufficient.
ktc = KVTransferConfig( kv_connector="SharedStorageConnector", kv_role="kv_both", kv_connector_extra_config={"shared_storage_path": "local_storage"}, ) llm = LLM(model="...", kv_transfer_config=ktc)

10. Benchmarking & Tuning

Everything above is a lever. This module is how you find out whether pulling it actually helped - and it's the part most people skip until something's already on fire in production.

The metrics that actually matter

MetricDefinitionMatters most for
TTFTTime to first tokenInteractive UX - the "is this thing alive" feeling
ITLInter-token latencyPerceived streaming smoothness
TPOTAverage ITL across the responseSummarizing overall generation speed
ThroughputTokens or requests per secondOffline / batch workloads, cost per token
GoodputThroughput that meets your actual SLOsThe number that should be in your dashboard, not raw throughput
Below the saturation batch size, you're paying for streaming weights off HBM - latency barely moves. Past it, you're compute-bound and every added token costs real time.
The Practical Move Use vllm bench latency to measure single-batch response time, vllm bench throughput to find your ceiling under saturation, and vllm bench serve to simulate realistic arrival patterns and measure goodput against real SLOs. Don't tune against throughput alone - a config that maximizes throughput can blow your TTFT budget for interactive use cases.
vllm bench latency \ --model <model-name> \ --input-tokens 32 \ --output-tokens 128 \ --batch-size 8 vllm bench throughput \ --model <model-name> \ --input-len 512 \ --output-len 128 vllm bench serve \ --model <model-name> \ --request-rate 4 \ --num-prompts 200

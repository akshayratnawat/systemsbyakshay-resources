Your RAG knowledge base changes every week. How to ship updates without breaking production

A RAG update that goes wrong does not throw an error. The bot keeps answering, fast and confidently, from the wrong version of your documents. This post shows where that happens and how to ship weekly updates without it.

The problem, in one example

A company runs an HR assistant on a RAG knowledge base. The leave policy says employees can carry over 10 unused leave days. In March, HR publishes a new policy: the limit is now 5.

The team uploads leave_policy_v2.pdf into the same index that already holds leave_policy_v1.pdf. The ingestion job reports success. Dashboards stay green: latency is normal, the error rate is zero, and users keep getting answers.

Then an employee asks: "How many leave days can I carry over?"

The retriever returns chunks from both versions. The v1 chunk is the closer semantic match, because its wording matches the question more directly. The model answers "10 days" and cites a real company document. Nothing looks broken, and the answer is wrong.

That is the whole problem: the failure is silent, and it looks like success.

Where it breaks

Your knowledge base is two stores, not one: the source (files, wiki, database) and the index (chunks plus embeddings). Updating the source does not update the index. Every gap between the two is a place for a stale answer.

Failure What happens Why nobody notices
Replaced document, old chunks kept v1 and v2 both sit in the index and compete at retrieval The answer cites a real document, so it looks grounded
Deleted source, chunks kept A withdrawn policy keeps getting quoted The source is gone, so no one checks it
Document got shorter Re-chunking writes 9 chunks, but old chunks 10 to 14 stay Leftover chunks have valid embeddings and rank normally
Two embedding models in one index New and old vectors are not comparable, so ranking quietly degrades Retrieval still returns results, just worse ones
Editing the live index Users query a half-updated index while the job runs The window is short, so it passes as a one-off glitch
No way back A bad update stays live until someone rebuilds There was never a previous version to return to

Two of these are not hypothetical for Azure AI Search. An indexer does not track object deletion in the data source, so deleted files can leave orphan search documents (Microsoft docs). And if the deletion policy is not set before the first indexer run, documents deleted earlier stay in the index even if you add the policy later and reset the indexer (Microsoft docs).

None of these show up in latency, error rate or token cost. They show up as answers that are wrong in a way users cannot see, which is why the fixes below test the answers, not the pipeline.

Fix 1: build a new index, never edit the live one

The rule: your app never queries an index by its real name. It queries an alias (for example kb-live). Every update builds a brand-new index (kb-2026-11-26), tests it, and only then moves the alias.

Step 1: Put the right fields on every chunk

You cannot clean up what you cannot find. Give every chunk these fields, all filterable (in Azure AI Search, mark the fields filterable; in Pinecone, store them as record metadata):

Field Example Used for
chunk_id (key) leave_policy#007 Unique key per chunk
doc_id leave_policy Delete or replace every chunk of one document
source_version v2 Know which version an answer came from
content_hash a91f... Skip re-embedding unchanged chunks
embedding_model text-embedding-3-large Catch mixed models in one index
ingested_at 2026-11-26 Freshness tracking

Step 2: Decide what kind of update this is

  • Content only (new, edited or deleted documents): rebuild from the source into a new index, but reuse stored embeddings for chunks whose content_hash did not change. This is where most of your embedding cost goes, so cache it.
  • Pipeline change (new embedding model, new chunk size, new schema): re-embed everything. Never mix old and new vectors in one index, because they are not comparable.

Step 3: Create the new, empty index

  • Azure AI Search: Read the definition of the live index, copy it, change only the name (for example kb-2026-11-26), and create the new index from it. Do not retype the schema by hand, or the two indexes will drift. Run the new index side by side with the live one, then redirect your application to it once it passes.
  • Pinecone, fresh index: Create a new index whose dimension and metric match your embedding model. Use this whenever the embedding model or the chunking changes. Alternatively, take a backup of the live index and restore it into a new index. The restored index must keep the source's dimension, metric and vector type, so use the copy only when the embedding model stays the same.

Step 4: Fill it from the source, not from the old index

Run your ingestion against the new index. Because you start from the source, replaced and deleted documents cannot leave old chunks behind, which is the whole point. Reuse stored embeddings for chunks whose content_hash did not change.

  • Azure AI Search: If you use an indexer, point it at the new index. Turn on deletion detection on the data source from the very first run.
  • Pinecone, fresh index: Upsert every chunk of every current document into the new index.
  • Pinecone, copy of the live index: For each document that changed or was removed, first delete its old chunks, then upsert the new ones. Pinecone can delete records by ID, by metadata filter, or empty a whole namespace, so filter on doc_id to remove every chunk of one document at once.

Step 5: Sanity-check before any user sees it

  1. The total record count of the new index matches the number of chunks your pipeline produced (Azure: index statistics, Pinecone: index stats).
  2. Every doc_id in the index exists in the source list, and the reverse. A mismatch means orphans or missing documents.
  3. Only one value of embedding_model appears.
  4. Spot-check three documents you know changed.

Step 6: Run the gates, then switch the pointer

Run Fix 2 and Fix 3 below against the new index, by its real name. If they pass, move the pointer your app reads.

Step 7: Keep the old version for rollback

Do not delete the old index or namespace right after the switch. If groundedness drops or users report a wrong answer, rollback is changing the pointer back. Delete the old version after a few days of clean monitoring.

Fix 2: a question set is your gate (quick hack)

Before any index goes live, ask it questions you already know the answers to. If a question that passed on the old index fails on the new one, the update does not ship.

How to start: open your support tickets or chat logs and copy 20 real questions. Write the expected fact next to each one. Add a new row every time something breaks in production, so the set grows from your own failures.

Question Must say Must not say Type
How many leave days can I carry over? 5 days 10 days changed
What is the notice period for resignation? 60 days stable
Who approves remote work? line manager stable
What is the policy on crypto reimbursements? "I don't know" no_answer

Three rules make it work:

  1. Run the same set on the old and the new index. Compare the two results, not just a pass mark. A question that passed before and fails now is a regression, and it blocks the swap.
  2. Include no_answer questions. For things your knowledge base does not cover, the right answer is "I don't know". Most RAG systems fail here first, and a deleted document turns a good answer into one of these.
  3. Include changed questions for every document you touched. These are the ones the update is supposed to fix.

How to run it, every update:

  1. Ask every question on the old index and write down whether each answer passes.
  2. Ask the same questions on the new index.
  3. Mark an answer as a pass only if it contains the "Must say" text and none of the "Must not say" text.
  4. List every question that passed on the old index and fails on the new one. That list is your regressions.
  5. If the list is not empty, fix the cause or hold the update. The alias or config value does not move.

A spreadsheet is enough to start. Automate it once you run it every week.

Check answers with simple string rules first (Must say, Must not say). Only add an LLM judge for questions where the wording varies, and spot-check the judge yourself.

Fix 3: challenge the update with deletes and replacements (15-minute hack)

Fix 2 checks what you thought to ask. Fix 3 checks the exact documents the update touched, and it needs no LLM, only retrieval.

Your ingestion job already knows which documents were replaced and which were deleted. Turn that list into automatic tests:

Update type Challenge query Pass condition
Document deleted A question that used to hit it No returned chunk has that doc_id
Document replaced A question whose answer changed Every returned chunk from that document has the new source_version
Document shortened The same document, a question about the removed part No chunk numbered above the new chunk count exists
Any update One question per touched document Top result comes from the expected doc_id

How to run it, every update:

  1. Take the list of documents this update deleted, replaced or shortened. Your ingestion log already has it.
  2. Write one question per document. Ask the new index for its top 10 chunks, without involving the LLM.
  3. Deleted document: none of the 10 chunks may come from it.
  4. Replaced document: every chunk that comes from it must carry the new version.
  5. Shortened document: no chunk numbered beyond its new chunk count may exist.
  6. Any failure blocks the switch.

Where do the sample questions come from? Take the first heading or sentence of each changed document and turn it into a question, or ask an LLM to write one question per document once, then store it. These tests run in seconds, so run them on every update, not only the risky ones.

How to track it: watch the answers, not the servers

In the opening example, latency and error rate stayed green while the answers were wrong, so a standard infrastructure dashboard would have missed it. This mockup shows the two signals that catch a bad update fastest, plus the index status that tells you what to roll back to.

Mockup with illustrative sample data, not from a real system. 14 days.

The update shipped on day 8 without a gate. Groundedness fell under the alert line and outdated citations stayed high for three days. Because the app queries an alias, the rollback on day 10 was one pointer change, and both signals recovered the next day.

Track these five signals:

Signal How to compute it Starting alert
Groundedness Share of claims in sampled answers supported by the retrieved chunks, scored by an LLM judge on a small slice of traffic Below 0.85
Outdated-answer rate Share of answers whose top source chunk has a source_version older than the current one for that doc_id Above 5%
Gate result per update Number of regressions from Fix 2 and Fix 3 Any above 0 blocks the swap
"I don't know" rate Share of answers that decline to answer A sudden drop after a delete, or a spike after an update
Index freshness lag Time between a source document changing and its chunks being live Above your update schedule

The alert values are starting points for the example, not benchmarks. Set yours from two weeks of your own baseline, and note that the outdated-answer rate only works if you stored source_version on every chunk in Fix 1, step 1.

The checklist before your next update

  • Every chunk carries doc_id, source_version, content_hash and embedding_model
  • The app queries an alias, never a real index name
  • Each update builds a new, versioned index from the source
  • Deletion detection was on from the first run (Azure indexers do not track deletions by default)
  • A question set, including "I don't know" questions, runs on the old and the new index
  • Challenge queries cover every deleted, replaced and shortened document
  • The old index stays for a few days, so rollback is one alias change
  • The dashboard tracks groundedness and the outdated-answer rate, not only latency

A RAG system is only as current as its last successful update, and "successful" has to mean the answers are right, not that the job exited with zero errors.

Agent Skill Evals

50,000+ public agent skills got audited. Almost none had a test. Here's the 2-file pattern that fixes yours.

1. Why Skills Fail Silently

Agents are non-deterministic. Same skill, same prompt, different outcome depending on the run. So when a task fails, you genuinely can't tell if the skill is bad or the task was just too hard for the model. Most people never separate the two, which means every "skill" sitting in your agent's toolkit could be quietly making it worse and you'd have no way to know.

The Diagnosis Problem
task_failure = f(bad_skill) OR f(hard_task) - and you can't tell which
SkillBench audited 50,000+ public agent skills. Almost none had a test. Most were never even reviewed by a human. Most were AI-generated - written by an agent, accepted because they read well, never checked against a single case.

2. Capability Skills vs. Preference Skills

Every skill you write falls into one of two buckets, and it changes how you should treat it.

TypeWhat it doesLifespanEval priority
Capability skillTeaches the model something it can't do consistently yet - tracing logs, scaffolding a new app, using a brand-new API released after training cutoff.TemporaryRetire it as the base model improves. Run the eval with the skill off periodically - if performance holds, delete the skill and keep the eval.
Preference skillEncodes something a model will never guess on its own - your team's workflow, your style guide, your domain rules, your company's specific conventions.DurableProtect it. Foundation models will never absorb domain-specific knowledge on their own, so these need permanent regression coverage.
The test: if you don't know which bucket a skill belongs to, you don't know when it's safe to delete - and you're probably not evaluating it correctly either.

4. The Eval Harness Pattern (Copy This)

You only need two files: a JSON test suite and a small runner script. This is the exact pattern Google DeepMind's own team used to build a skill for Gemini's new Interactions API - a surface released after the model's training cutoff, so it had zero built-in context on it. 117 test cases, one JSON file, one Python script. Result: ~90% valid code on the new API, up from near zero.

File 1 - test_cases.json

[ { "prompt": "Build a multi-turn chat feature using the Interactions API", "language": "typescript", "should_trigger": true, "expected_checks": [ "uses_interactions_sdk", "no_deprecated_model_id", "session_state_handled" ] }, { // negative case - skill should NOT fire here "prompt": "Write a function to reverse a string in Python", "language": "python", "should_trigger": false, "expected_checks": [] } ]

File 2 - run_eval.py (the shape of it)

# 1. Load test_cases.json # 2. For each case: spin up a clean coding-agent workspace # 3. Feed the prompt, capture whether the skill triggered # 4. If should_trigger doesn't match actual trigger -> fail, log it # 5. Run each expected_check as a cheap regex/string assertion # against the generated code (no LLM-as-judge needed for most checks) # 6. Run every case 2-6x - agents are non-deterministic, # one pass tells you nothing about reliability # 7. Print pass rate. Compare against the last run before you # change the skill file.
Why regex over LLM-as-judge: most skill assertions are checking for a specific SDK, a specific method name, an absence of deprecated patterns - things a cheap string match catches reliably. Save LLM-as-judge for the cases that genuinely need judgment (tone, structure, multi-step correctness), not for "did it use the right function name."

5. How to Talk About This at Two Different Tables

To your manager

"It's a small test file that checks whether the shortcut we gave the AI is actually helping, instead of us just guessing."

In an interview

"An eval harness for a skill: a JSON test suite with prompts, expected trigger behavior, and assertions, run against the agent with and without the skill loaded, multiple trials per case to account for non-determinism."

6. Ship a Skill Like Code - The Full Checklist

  • Write the description as why + how + when - not vibes. The description is the only part of a skill the model pays a token cost for on every single call, so it has to earn that cost.
  • Directives, not essays. "Use the Interactions API if the user is building multi-turn chat" beats "The Interactions API is recommended for multi-turn use cases."
  • Layer it. Description first (always loaded), then the skill body (loaded when triggered), then reference files (loaded only when the model needs that specific depth - e.g. one reference per cloud provider, not one giant deploy doc).
  • Give goals, not steps. If the exact same steps run every single time with no variation, it's not a skill, it's a script. Write the script and tell the model to call it.
  • Test 5 yes-cases and 5 no-cases, minimum. Negative cases catch over-triggering, which breaks agents as often as a skill that never fires at all.
  • Pull real cases from production traces once you have them - nothing beats real user prompts for finding the trigger conditions you didn't think of.
  • Kill the no-ops. Delete every instruction that doesn't actually change agent behavior ("write clean, readable code" - the model already tries to do this without being told).
  • Run every eval case multiple trials (2-6x), not once. One pass tells you nothing about a non-deterministic system.
  • Test across harnesses if your team uses more than one coding agent - a skill that works great in one harness can fail in another.
  • Retire on schedule. Periodically run the eval with the skill switched off. If performance holds without it, delete the skill and keep the eval - the eval tells you the moment you need to bring it back.

7. Interview-Ready Q&A

QuestionThe answer that shows depth
Why can't you just eyeball whether a skill works?Agents are non-deterministic - a single successful run doesn't prove reliability, and a single failure doesn't prove the skill is bad rather than the task being genuinely hard. You need repeated trials with and without the skill to separate signal from noise.
How do you decide if a skill should be temporary or permanent?Ask whether it's teaching a capability (temporary - retire as the model improves) or encoding a preference/domain rule (durable - a foundation model will never learn your team's specific conventions on its own).
Why do AI-generated skills tend to underperform?They're often full of "no-ops" - instructions that read well but don't change model behavior - and they're rarely tested against negative cases, so they over-trigger or fail silently in ways nobody catches before shipping.
